Offline Customer Detail Management App

Objective
Develop a cross-platform application (Windows .exe and Android .apk) for an insurance client to securely store and manage customer details offline, featuring a local Wi-Fi database and file sync.

Proposed Architecture
- Framework: Flutter (Dart) - Allows building both Android and Windows native apps from a single codebase.
- Local Database: Isar (NoSQL) - High-performance, cross-platform NoSQL database optimized for Flutter. Excellent for offline-first applications.
- File Storage: Local app directory storage for images, utilizing relative paths to decouple files from absolute device structures.
- Sync Mechanism: Local Wi-Fi sync using mDNS (Multicast DNS) for device discovery and a lightweight internal HTTP server for data and binary file exchange. 
- Conflict Resolution: "Last Write Wins" based on globally unique identifiers (UUIDs) and updatedAt timestamps for every record.
- Security: App-level password protection. The password hash is stored securely via flutter_secure_storage. No external auth servers.

Phase 2: Database Layer (Isar) & File System
1. Define the Company schema:
   - id, uuid, name, updatedAt, isDeleted.
2. Define the Customer schema. Required fields:
   - id: Fast auto-incrementing local ID (for Isar requirements).
   - customerId: A business-level identifier (String, e.g., "CUST-001") for search purposes.
   - uuid: Universally Unique Identifier (String, crucial for syncing).
   - name, contactNumber, email, etc.
   - Assigned Company: Reference to the Company schema to map the customer to their respective insurance provider.
   - Dates: dateOfBirth, anniversaryDate, nextMeetingDate (DateTime).
   - Rich Content: generalNotes, meetingNotes (String).
   - UI Data: Fields to support checkboxes (Booleans) and radio selections (Strings/Enums) for policy specifics.
   - Documents/Images: Embedded list of CustomerDocument objects containing:
     - documentName: Label or type of document (e.g., "Aadhaar", "Pan Card").
     - fileName: The local filename of the saved binary image.
   - updatedAt: Timestamp (DateTime, crucial for conflict resolution).
   - isDeleted: Boolean (Soft deletes).
3. Implement repository functions for Create, Read, Update, and Delete across all schemas, ensuring local file system operations (saving/deleting images) are tied to database transactions.

Phase 3: Security & Password Lock
1. Implement a lock screen that appears on app startup and when returning from the background.
2. Store the user's defined password (hashed) using flutter_secure_storage.
3. Provide an initial setup screen if no password exists yet.

Phase 4: Wi-Fi Discovery & Syncing
1. Discovery: Use the nsd (Network Service Discovery) or bonsoir package to broadcast a local service.
2. Data & File Transfer Server: Spin up a lightweight HTTP REST server (shelf package) on the host device.
   - Create endpoints for fetching JSON data.
   - Create endpoints for downloading/uploading binary image files.
3. Merge Logic:
   - Device A connects to Device B.
   - Data Sync: Exchange full lists of customer records. For every record matched by uuid, compare updatedAt. The newest record overwrites the older one.
   - File Sync: Parse the imageFileNames from the latest records. If a device is missing an image file, it requests the binary file via the HTTP server and saves it locally.

Phase 5: Build & Packaging
1. Generate the Windows .exe using flutter build windows (packaged optionally with Inno Setup or MSIX).
2. Generate the Android .apk using flutter build apk --release.

Verification & Testing
- Dashboard Integrity: Create customers with dates in the near future and verify they appear correctly on the upcoming events dashboard.
- Rich Form Handling: Verify images can be selected, saved, and rendered correctly from local storage. Test all checkboxes, dates, and radio inputs.
- Offline & Security Integrity: Verify app operates entirely offline and locks appropriately.
- Complex Sync Simulation: Connect two instances. Modify records on both ends, attach a new image on Device A, and trigger a sync. Assert that both devices have the exact same database state and the same image files in their local directories.
